# Bug audit

High-confidence correctness bugs only, read against `86072bc`. Each one was checked in the code it names. Deliberate behavior in `CLAUDE.md`, `.claude/rules/`, and the open items in `docs/TODO.md` is not listed. Nothing here has been fixed.

The pass covered the engine, codec, catalog, DSP, analysis, window, bus, Discord, MCP, vault, PipeWire, online client, listener, lyrics, equaliser, providers, and the binary. DSP, analysis, the vault's kept-decoder reuse, PipeWire's packer, and the online mappings did not produce a bug that cleared the bar.

## Playback and the window

- **An album plays in the listing's sort while it is drawn in disc order.** `album_rows` in `crates/resonate-ui/src/models.rs` sorts an opened album by release disc and position, then by the tags, and that is the list `views/browser.rs` draws. The album heading still offers Sort (`hero_actions` with the sortable flag set). Play, Play next, and Add to queue go through `with_everything_listed` and `play`, which load `listing()` from index 0 in the tracks pane's sort. A row click and Enter do the same from `listed_track_at`: the track under the pointer starts, and everything after it is the sort order, not the rows under it on screen. With the pane on Title, the first row can be track 1 while Play starts at the first title. The same split happens on the default album order when a paired release seat disagrees with the tag numbers. Queue the `ListedRow::Held` run in the order the list draws, and draw that order when it is the one Sort selected.

- **A queue that plays through is resumed from the first track.** `Queue::advance` sets the cursor to `None` when the last row ends and repeat is off. `Engine::skip` then `stop`s, and `publish` reports `queue_position: None`. `Keeping::kept` reads that as row `0` and, with the track cleared, frame `0`, and writes `Keep::Place` because the row changed. The window's observer stores it. The next bare `resonate` opens track 1 at the start. Leave a sample with no queue position unstored, so the last real place remains.

- **Stop on Listen does not stop once the clip has been taken.** Stop is drawn while `is_listening` is recording or asking (`views/listen.rs`). `ListenModel::stop` only calls `Hearing::stop` in the recording stage. Closing the sheet calls that same `stop`. After the clip is in, the recognition task still runs, `landed` still tells the desktop, and the sheet still moves to the found song. Drop the in-flight task on Stop and on close, and apply the result only while that listen is still current.

- **A lyric lookup that finishes after the tags land rewinds the sheet.** `LyricsModel::follow` rewinds only when the track id changes, so a digest landing mid-track can refine the search and leave the scroll. The completion of `_find` calls `rewind` on every result. A sidecar already on screen jumps back to the top when the tags arrive and the second lookup returns. Rewind only when the track changed.

- **Wanting a second found song leaves the first mark stuck.** `want_found` inserts the recording into `wanting` and stores the lookup in the single `_wanting` task. Wanting another song before the first returns drops that task, so the first id is never removed. Its control stays the greyed wanting mark for the rest of the run. Keep a task per recording, and always remove the id of the one that finished.

- **Going back to a search lets the in-flight lookup replace its results.** `ask_elsewhere_after` returns immediately when `found_for` is already the text, and does not cancel `_finding`. After "echoes" has landed, editing to "echoesx" starts another lookup and leaves `found_for` as "echoes". Backspacing to "echoes" before that returns takes the early path. When "echoesx" completes it writes `found` and `found_for` unconditionally. `found_here` then answers nothing, because the stored text is no longer the query, and the songs already found for "echoes" are gone until the text changes again. Cancel the in-flight ask when the early path is a different query, and store a result only while that text is still the one being asked.

## The catalog

- **A rescan indexes the file's names over the name the lookup kept, and points the row at the file's artist.** The upsert in `store::track` keeps `tracks.title` and `tracks.artist` when the row is answered and `tagged_title` / `tagged_artist` have not moved. `artist_id` is assigned from the file on every update. `apply` then calls `index`, which writes `title(record)` and `indexed_artist(record)` — the file, or the stem — into `tracks_fts`. A file the lookup renamed still shows the corrected title, and a search for that title misses it. The artist page is the file's artist again. Have the upsert return the title, artist, and artist id it left on the row, and index those.

- **A second delivery of one vault object is indexed under the later want.** `note_delivered` inserts the track and, on `ON CONFLICT(path, span_start)`, updates nothing but `seen` and returns the existing id. It then `index_row`s that id with the current want's title, artist, and album. The row stays the first want's; the search row becomes the second's. Searching the album the track is filed under misses it. Skip the index on the conflict path.

- **An equal-rank date keeps the oldest tag.** `Builder::date` stores a new value only when its rank is strictly more specific than the one held (`*held <= rank` leaves the slot). Revisions are absorbed oldest first, and a WAV `INFO` list is absorbed before them. Two `DATE` / `TDRC` / `TYER` values of the same kind leave the earlier one. A file retagged from 1971 to 2011 still reads as 1971, and that is the year stored and matched by `year:`. Keep a strictly more specific date, and let an equal rank replace.

- **A later blank ReplayGain erases a gain already read.** `given` leaves a text slot alone when the value is blank. The four ReplayGain arms assign `decibels` / `peak` directly, and both return `None` for a blank or unparseable string. A real `REPLAYGAIN_TRACK_GAIN` followed by an empty frame, in the same block or a newer revision, clears the gain and the peak. The track is played with no ReplayGain. Write the new value only when it parses.

## The command line and the bus

- **A `file://` argument is not the path a plain argument is.** `location_of_argument` keeps whatever `MediaLocation::from_uri` decoded. A plain path goes through `from_here`, which canonicalizes when the file exists. `resonate play file:///home/user/Music/a.flac`, `resonate queue` of that URI, and a bare `resonate` handed `%U` therefore keep a symlink component. The catalog row is the canonical path the scan stored, so the queued row is unscanned: library tags, play counts, and resume do not attach. `.` and `..` in the URI are kept the same way. Run a local `file://` path through `from_here` after it parses.

- **`#frames=` is dropped on the way into the queue, and a bad cut is analysed as the whole file.** `from_uri` cuts the URI at `?` or `#`. `queue_items` uses that, so `resonate play 'file:///music/Meddle.flac#frames=588-44100'`, `resonate queue` of that URI, and opening it in the window all queue the whole file with no span. That fragment is the URI a cue row is published under. `resonate analyse 'file:///music/a.flac#frames=100-50'` makes `from_uri_within` return nothing because the end is not after the start, then the same strip succeeds, and the command analyses the entire file. Build queue rows from `from_uri_within`. If the argument contains `#frames=` and the span does not parse, `analyse` should refuse it.

- **`playlist --add` stores a `.cue` as one row.** `extend` canonicalizes each path and inserts `Cut::whole`. `resonate play album.cue` and `resonate queue album.cue` both go through `sheet_items` and queue each cut. `resonate playlist Mixtape --add album.cue` stores the sheet. Playing the playlist then tries to decode the sheet as audio. `--add` should use the same sheet expansion as `queue_items`.

- **The bus cover cache answers by track id alone.** `Pictures::laid_down` returns the stored URI as soon as the track id matches, without looking at the bytes. Unscanned loads mint from an empty set, and the first id is `TrackId::MAX` (`unclaimed_id(&[])`). The next unscanned queue in the same process reuses that id while the old file is still among the eight kept covers, and `mpris:artUrl` and the notification publish the previous picture. Treat an id hit as valid only when the stored file is the digest of these bytes.

- **A starved count can be published as zero and then dropped.** The ring raises `Underrun` and only then `fetch_add`s the missing frames on `starved` with `Relaxed`. The push synchronizes writes that happened before it, so the add is not ordered with the fault. `collect_faults` drains faults, `swap`s `starved` to 0, and returns without recording `missing` whenever no fault was in that poll. An underrun observed between the push and the add is published as `Underrun { missing: 0 }`. The next poll sees the frames with no new fault and throws them away, so `OutputStatus::went_without` stays short of what the graph missed. Add the frames before raising the fault, with a release on the add and an acquire on the swap, and record a non-zero `missing` while playing even when this poll saw no fault.

## Considered and rejected

- **Previous on the first track restarts it, and under track repeat it wraps.** `retreat` stays on row 0 when there is no previous row, and `Command::Previous` then starts at frame zero. With the default skip policy, a hand skip turns track repeat into queue repeat before that move, so the first row wraps to the last. Both are the skip rule, not an accident.
- **A real directory and a symlink to it are both walked when `follow_symlinks` is on.** The visited set records a symlink target, not a directory entered directly. The binary and the window always pass `follow_symlinks: false`, so the shipping scan never follows the link.
- **The one-pass integer level mask, the AutoEq maker-dropped tail, the kept-form decoder reuse, and the in-place DoP pack** match the behavior they replaced.
- **Skipping the track-list diff when the queue `Arc` is unchanged** matches `publish_queue`, which stores a new `Arc` only when the revision moves. Metadata and late tag reads are still published on that poll.
